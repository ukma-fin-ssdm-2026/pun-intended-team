# ADR-001: Modular Monolith with a Separate Import Service

**Status:** Accepted

## Context

- SEC-001, SAFE-001 and SAFE-002 must hold even when the API is called directly, and FUNC-002 must hold under concurrent requests, so every business rule lives on the server ([high-level design §1](../high-level-design.md)).
- Core work — requests, matching, notifications — is light at Kyiv scale; the only CPU-bound part is bursty matching rounds.
- Event import parses untrusted external input and may require scraping (R-001).
- A separate notification service was judged overkill for a single-repo system.

## Decision

Two processes built from **one codebase and one image**, selected by a `ROLE` setting:

| Process | Instances | Runs |
|---|---|---|
| **Main server** | 1 at launch, scales horizontally | API, matching, notifications, all core background jobs |
| **Import service** | 1 | Provider import, normalization, staleness marking |

1. Modules are split by domain and talk only through their interfaces; none reads another's tables.
2. Background jobs go through a Postgres-backed queue (pg-boss); a job runs once across instances, so no hand-written locks.
3. The round algorithm runs in a Node worker thread, so a round never blocks the event loop (PERF-001).
4. The two processes never call each other. Import writes its own tables and publishes facts (`event.changed`); the main server decides what they mean.
5. The import service has a database role limited to event tables and no access to encryption keys (SEC-003).

## Alternatives

| Option | What it does better | Why not |
|---|---|---|
| Thin server, rules on the client (e.g. a backend-as-a-service) | Less server code | SEC-001, SAFE-001, SAFE-002 and FUNC-002 cannot be enforced on a client the user controls |
| Microservices, one per domain | Independent deployment and scaling per domain | A match, its inbox rows and its jobs would span services, so the single transaction (ADR-002) and the per-session lock (FUNC-002) turn into distributed coordination; far more to operate than the load needs |
| Separate notification service | Push failures isolated from the API | Notifications are written in the same transaction as the change that causes them; push is already a retried job, so a separate process adds a deployable and isolates nothing |
| One process, import included | One deployable fewer | Untrusted provider input and scraping (R-001) would run with access to personal data and encryption keys (SEC-003) |

## Consequences

- One deployable fewer than a service split; failures of the main server take down all core features together, but no queued work is lost.
- Requests and jobs share CPU on the main server.
- **Scale-out trigger:** a second main-server instance is added when PERF-001 k6 results approach the limit or monthly uptime approaches REL-001. Nothing in the code changes — the server is stateless, pg-boss runs each job once, and the per-session lock lives in Postgres.
- **Split trigger:** if the PERF-001 k6 run under a round burst breaks p95 ≤ 1 s, run the jobs under a separate `worker` role. Only the deployment changes.
- **Merge trigger:** if providers give us real APIs and the threat model no longer needs the isolation, import can run inside the main server the same way.
