# ADR-005: Staging on One Server with Docker Compose

**Status:** Accepted

## Context

The API only runs on developers' machines, so the app, the MCP server and teammates cannot reach it from anywhere else. Staging needs a public HTTPS address, PostgreSQL with backups (REL-004), TLS (SEC-001) and the per-IP limits behind a proxy (SEC-007). The team pays for it itself ([external services](../../operations/external-services.md)): a managed database or a load balancer would cost more than the server. The host is not settled yet: the AWS account is still being verified, and Hetzner Cloud is the fallback, so nothing may depend on one provider.

## Decision

**Staging is one Linux server running Docker Compose; CI publishes one image per commit and deploys it over SSH.** Setup and operations: [staging](../../operations/staging.md).

- Caddy terminates TLS with a Let's Encrypt certificate it renews itself and is the only service reachable from outside. The API trusts its `X-Forwarded-For` through `TRUST_PROXY`, so the per-IP limits count clients, not the proxy.
- PostgreSQL runs in a container, its data in an external volume. A backup service keeps 7 daily and 4 weekly `pg_dump` copies, and every deploy takes one first.
- One image runs the API, the migrations and the import. After every green build of `main`, CI pushes it to GHCR tagged with the commit. The image is private: each deploy job logs the server in with its own short-lived token, so the server keeps no registry credentials, and a rollback is a manual run of the Deploy staging workflow.
- The Deploy staging job renders the server's `.env` from the committed template `deploy/staging.env` with the secrets of the GitHub environment `staging`, writes it over SSH and runs `deploy/deploy-staging.sh <commit>`. Migrations run before the API starts. If the API is not healthy within 2 minutes, the script starts the previous version again and the job fails.
- The key files are created on the server on the first deploy and kept there and in the team vault, not in GitHub.

## Alternatives

| Option | What it does better | Why not |
|---|---|---|
| Managed PostgreSQL (RDS) | Backups, encryption at rest and failover out of the box | Costs more than the server; Hetzner has none |
| PaaS (Render, Railway, Fly.io) | No server to look after | Priced per service; PostgreSQL, the API and the import add up past one server |
| Build the image on the server | No registry, no CI job | The server needs the whole repo and the memory to build; a rollback means building again |
| Secrets only in the server's `.env` | Nothing secret in GitHub | Changing a value means logging in to the server; CI could not deploy |

## Consequences

- A merge to `main` reaches staging in minutes, and any published commit can be deployed again to roll back.
- The server is a single point of failure, and staging is down while it restarts.
- The high-level design's §6 is not met in full: the database is not managed, the backups stay on the same server, and the volume is encrypted at rest only if the provider does it (SEC-003). The 1000-requests-a-minute backstop of SEC-007 is not enforced.
- A rollback does not undo migrations, so it only works while the older code still fits the database. A failed migration stops the deploy before anything is replaced, and has to be resolved by hand before the next one.
- **Reconsider when** the app goes to production: copy backups off the server, decide on encryption at rest and add the backstop limit.
