# ADR-002: PostgreSQL as the Single Data Store

**Status:** Accepted

## Context

What the design needs from storage:

| # | Need | Source |
|---|---|---|
| N1 | Multi-row ACID transactions — a match, its inbox rows and its jobs commit together | Matching, notifications, ADR-001 |
| N2 | Row and advisory locks — one per-session lock for instant match and rounds | FUNC-002 |
| N3 | Job queue in the same database | ADR-001 |
| N4 | Relational integrity across users, sessions, applications, matches, exclusions, reports | FR-016–FR-031 |
| N5 | Ad-hoc filters over category, date and location | FR-007 |
| N6 | Geo queries for map pins | FR-012 |
| N7 | Semi-structured raw provider records | FR-008, FR-015 |
| N8 | Encryption at rest, managed backups, point-in-time restore | SEC-003, REL-004 |

Scale is small: one city, 500 concurrent sessions (A-001).

## Decision

**PostgreSQL** with **PostGIS** (N6) and **JSONB** (N7), as the only data store — including the job queue.

## Alternatives

| Option | What it does better | Why not |
|---|---|---|
| MongoDB | Varied document shapes (N7) | Weak on N1–N4; JSONB already covers N7 |
| Cassandra | Massive write throughput across data centres | No multi-row transactions or ad-hoc filters; nothing we need |
| Neo4j | Multi-hop traversals | Our interest overlap is one hop — a join over a few hundred rows |
| Redis (as an addition) | Shared counters and caching | Per-IP rate limits go to the load balancer; account lockout stays in Postgres |

The deciding argument: **any second store breaks the single transaction** behind N1 and N3, and would require an outbox and cross-store consistency.

## Consequences

- One system to back up, secure and monitor.
- Sensitive fields (phone number, usernames, date of birth) are encrypted at column level with keys from the main server's env file (SEC-003). Because encryption uses a random IV, each encrypted phone number has an HMAC `contact_hash` that carries the unique index and every lookup. Photos are stored in their own table rather than on the app host. Details: [data model §2 and §4](../data-model.md).
- Matching, notifications and jobs rely on Postgres-specific features (advisory locks, `SKIP LOCKED`); moving off Postgres later would be costly.
- **Reconsider if:** a multi-hop recommendation feature appears (try the Apache AGE extension first), or rate-limit / cache load exceeds what Postgres and the proxy handle (add Redis).
