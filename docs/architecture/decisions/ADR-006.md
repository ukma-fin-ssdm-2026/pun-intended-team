# ADR-006: Event Import Sources

**Status:** Proposed

## Context

- FR-008 asks for events imported from external listing services, naming Concert.ua as an example. The import (CMP-03, ADR-001) so far ran one adapter on a sample feed.
- ArtWizard gave the team access to its events API on 2026-11-03 (decision 9). The other sources offer no API, so for them the import reads public pages (R-001): it must stay within each site's robots.txt and load, and parse the schema.org `Event` data the sites publish for search engines rather than their markup (ADR-003: cheerio).
- Applicants are matched per event session. The same event imported from two providers becomes two catalog events, and the applicants of one copy never meet those of the other.
- Matching needs every venue on the map (FR-012); not every provider gives coordinates.
- The sources were compared on 2026-11-03: [event import sources research](../research/event-import-sources.md).
- Most imported events came without an end: on 2026-11-14 Karabas gave a real end for 3 of its 707 events and ArtWizard for 11 of 70, so the catalog showed "19:00 – 23:59" for concerts and plays. The start and end times of the sources were compared that day: [start and end times](../research/event-import-sources.md#start-and-end-times-410).

## Decision

1. **Two sources: ArtWizard and Karabas.**

   | Source | Decision | Why |
   |---|---|---|
   | ArtWizard (artwizard.io) | In, through its events API, with ArtWizard's permission (decision 9) | Lectures, exhibitions, workshops and other events ticket operators do not sell; coordinates for every venue |
   | Karabas (kyiv.karabas.com) | In | The ticket operator: concerts, theatre, cinema, sport, festivals, clubs; one section page carries the full JSON-LD of about 20 events |
   | Concert.ua | Out | Sells the same concerts as Karabas, so importing both would split applicants; needs one request per event; `@type` is `MusicEvent` for everything. `ConcertUaEventProvider` and its sample feed are removed |
   | Kontramarka | Out | No schema.org Event data; `Crawl-delay: 10` |

2. **Access.** ArtWizard: its events API, `GET https://api.artwizard.io/events` with the Kyiv events whose occurrences touch the coming 4 weeks (today and the 27 days after it, one day less than the catalog window, as decision 9's permission covers), 20 per page, every page of the answer up to 50; no event pages are crawled. The key is the secret `ARTWIZARD_API_KEY`: it is sent in the request URL only, and every logged URL and error shows it as `REDACTED`. Karabas, per its robots.txt: the seven Kyiv section pages, each page after page through its "load more" link with `per-page=20` added (without it, page 2 skips two weeks), until the last event of a page starts after the catalog window (the next page is counted from it; an event pinned to the top of a page may start later) or the page has no link, at most 40 pages per section; a link is followed only to the same section of the same host. Never `/ajax.php`, and not the sitemap, which lists mostly past events. Every request names the service in its User-Agent, waits at least 1 s after the previous one to the same site (Karabas `Crawl-delay: 1`), checked again after the wait since a timer may fire early, and is retried with backoff on network errors, 429 and 5xx. The HTTP client refuses a path the site's robots.txt disallows before sending it. Each adapter says whether it read the provider's **full list** for the window: not when a page failed or a page limit stopped the reading, nor when ArtWizard's pages hold fewer distinct events than its `total`. ArtWizard's paging can shift while the pages are read: on 2026-11-07 one event came on pages 1 and 2, so 83 records held 82 events against a `total` of 83, and another event was most likely never returned. A repeated slug is kept once and logged, so an event is never processed twice in a run, and such a list is not complete.
3. **Failures never stop a run.** A record that cannot be used is kept as a skipped record with its reason (FR-015); a provider whose list cannot be read (an ArtWizard API page that does not answer, a missing key) fails its own run only, and the other provider's run goes on (REL-003, FR-014). A run is recorded as failed whatever stopped it, and the error that stopped it is the one reported, even when the database cannot record the failure; a run the database could not finish at all, or whose process was killed, stays `running` and is marked failed when its provider's next run starts, so it never counts as succeeded.
4. **Categories** come from ArtWizard's `type` and from the Karabas section, not from `@type`, and the adapters name them by slug, which never changes, also when an administrator renames a category: `concerts`, `exhibitions`, `talks`, `workshops`, `cinema`, `theatre`, `stand-up`, `sports`, `festivals` and `parties` (Концерти … Вечірки, [data model](../data-model.md)). `volunteering` and `open-days` have listings only; an inactive category takes no imported events. Events with no matching category (e.g. children's events, excursions, circus) are skipped. One section also filters by `@type`: `/clubs/` lists talks, board-game nights, wine tastings and art evenings as a plain `Event` among its parties, so only its `MusicEvent` records become `parties` and the others are skipped with their `@type` as the reason (FR-015), without guessing from the title. An event listed in an earlier section keeps that section's category whatever its `@type`; `/clubs/` is read last.
5. **Times.** Both sources write Kyiv wall-clock time with a wrong offset (ArtWizard `18:00Z` for 18:00, Karabas `21:00+02:00` for 19:00). The adapters read the digits as Europe/Kyiv time.

   **An end is known or unknown.** It is known when the provider gives one, in one of three ways:
   - an ArtWizard `date_to` after its `date_from`;
   - a Karabas `endDate` with a time that is not midnight;
   - a length in the Karabas description (below), when the `endDate` gives no end.

   Otherwise the end is unknown, and the event says so: `events.end_time_known` is false, and `ends_at` is the end of the start day in Kyiv. That placeholder keeps sessions, cutoffs and the date filter (FR-007) working as before, so matching is untouched; how matching should treat an event without an end is not decided here. The API returns the flag as `endTimeKnown`, and the app shows only the start of such an event ("з 19:00") from the flag, not by recognising 23:59. An organization's event always has a known end.

   **ArtWizard.** An event lists its occurrences (`event_occurrences_data`), each of one of three kinds:
   - `date_from` equal to `date_to`: a start without an end, so the end is unknown;
   - a later `date_to`, the same day or after midnight: a known end;
   - 00:00 to 23:59:59, on the same day or a later one: no time given. ArtWizard writes 00:00 when the organizer gave no time, and an exhibition's run this way.

   The adapter imports the earliest occurrence with a time that starts in the catalog window, and logs an event with more than one occurrence in it. An event whose only occurrences in the window have no time is skipped for now as having no start time (FR-015). On 2026-11-14 that was 27 of 107 events, 19 of them exhibitions, and neither ticket site sold any of the 27 with a time, so a start cannot be taken from elsewhere. **Decided for #417 to implement:** an exhibition whose only occurrences in the window have no time is imported as a multi-day event that opens at a default time for exhibitions, 12:00 in Kyiv, from the later of the window's first day and the run's first day to the run's last day. The default is marked as one, by a start flag that mirrors `end_time_known` and that #417 adds, so the app can show the dates without a time. Until #417 lands these events stay skipped.
   - Not 00:00: the app would show a wrong time, and the matching rounds are anchored to the start, so they would be anchored to midnight.
   - Not skipped for good: most exhibitions running now would be missing from the catalog.

   **Karabas** writes its `endDate` midnights without the shift, so they are read as given; any other time is shifted like the start:
   - the next midnight means no end is given: the end is unknown;
   - a time later the same day is a known end (`21:00–23:00+02:00` is 19:00–21:00);
   - a later midnight is a run of shows from the start date to the day before it (e.g. "Тигролови", 3–12 November): only the first show is imported, with an unknown end, and the run is logged;
   - a time on a later day is a run of shows too, daily from the start time to that time of day, until that day (e.g. "Київський музей медуз", 10:00 on 14 November to 14:00 on 1 May): only the first show is imported, ending at that time on its first day, a known end, and the run is logged. An end time of day that is not after the start time (21:00 to 02:00 on a later day) is not read as a run: the end is unknown;
   - an `endDate` that is not after the start is ignored: the end is unknown.

   **A length in the Karabas description** gives the end when the `endDate` does not (the next midnight, a later midnight, or none): "Тривалість вистави – 1 год 20 хв" on a 19:00 play ends it at 20:20. On 2026-11-14 that was 199 of the 707 events, 172 of them plays. It is read conservatively:
   - only a length right after the word "тривалість", with at most a few words in between: hours and minutes ("1 год 20 хв", "1 година 10 хвилин"), tenths of an hour ("1,5 години"), hours alone ("2 год") or minutes alone ("90 хв", "110 хвилин");
   - only between 10 minutes and 12 hours;
   - not a length given as a bound ("від 1 години", "до 60 хвилин"); a note such as "без антракту" is not a length;
   - only when the event then ends on its start day: a 23:00 show of 2 hours keeps an unknown end, since the length may be of the programme and not of that night;
   - an `endDate` that gives an end always wins over the length.
6. **Images are linked, not copied.** `events.image_url` stores the provider's image URL and `events.source_url` its event page, which credits the provider and leads to tickets. The import never downloads an image. Neither does the API: it never copies, resizes or proxies an image, since images linked and not copied are a condition of ArtWizard's permission (decision 9) and its robots.txt disallows its image CDN. **Images are cached only on the client:** the app shows an event's cover with `expo-image` and `cachePolicy="memory-disk"`, so a cover already seen is not fetched from the provider again on every scroll or visit. That copy is the device's own browser-style cache, not a store the project keeps or serves from, and it lets the app spare the providers' servers. A cover that fails to load, e.g. one the provider removed, shows the coral gradient, as an event without an image does.
7. **Venues.** An event's venue is a saved imported venue whenever one fits, so the same place from both providers, or listed twice by one, is one venue. A saved venue fits when:
   - its **address is the same once normalized**: in lower case, without notes in brackets, punctuation, the kind of street (вул., вулиця, просп. …), the city (once or twice, so "вулиця Саксаганського, 6, Київ, Київ" from an earlier ArtWizard import is "вул. Саксаганського, 6") and initials ("С. Петлюри");
   - and its **name is similar**, compared in lower case, without quotes, brackets and the label "Місце проведення:" Karabas puts before some names. The same name always is. Otherwise the names must share a distinctive word, not one that only says what kind of place it is or describes it (будинок, театр, клуб, палац, центр, зала, pub, club, національний, драматичний …), so "Будинок Кіно" and "Будинок вчених" stay apart; and one name contains the other word for word ("Pepper's Club" and `Music Pub "Pepper's Club"`), or they share at least half of the distinctive words of the one with more ("Палац Україна" and "Національний палац мистецтв «Україна»").

   The same address alone is not enough: Реверб and Otel’ are in one building. An address without a house number (a Karabas address that is only "Київ") fits only a venue of the same name. Of several saved venues that fit, the oldest is taken, so the duplicates saved before this rule end up as one: their events move to it on their next run, and the other rows stay, never deleted, with no events. A saved venue whose coordinates lie outside Kyiv is taken only when none in Kyiv fits, and only for a provider venue with coordinates of its own, never for one that would take them over.

   ArtWizard gives every venue's coordinates, which replace the saved ones, often found by the geocoder for Karabas, unless they lie outside Kyiv: on 2026-11-08 ArtWizard placed "Печерськ Палац" about 300 km west of the city. Its venue address gets the city once, as some API addresses already end with it. A venue without coordinates and without a saved venue that fits (every new Karabas venue) is looked up through the `Geocoder` port, implemented with Nominatim at most once a second, within Kyiv. Its data is © OpenStreetMap contributors under the ODbL, so the attribution must appear where the app shows these coordinates. A venue it cannot find is skipped with the event. When the geocoder fails, e.g. because Nominatim cannot be reached, it is not asked again in that run: each lookup would wait for its retries and fail the same way, so the events at the other new venues are skipped with the reason "The geocoder is unavailable in this run" and one error is logged. Events at saved venues are still imported, and the skipped ones come with a later run.
8. **An event both providers list is saved once.** Before a provider's record becomes a new event, the import looks for a published imported event of another provider at the same venue (venues are already one row per place, decision 7) that starts at the same moment and has a similar title: the same words, or the words of one running on in the other, compared as venue names are (lower case, without quotes, brackets or punctuation), so "Bridgerton: Розкішний вечір музики при свічках" and "Bridgerton. Розкішний вечір музики при свічках", or "Гурт Третій Зайвий" and "Третій Зайвий", are one event, and "Німецька органна музика" and "Французька органна музика" are not. Such a record is not saved: it is kept as a skipped record "Duplicate of <provider> event <id>" (FR-015), so applicants of the event are not split between two copies. It still counts as seen (decision 10): the provider lists it, so it is no reason to cancel anything or to take the list as broken. The event that came first stays, whichever provider it is from; in a run ArtWizard comes before Karabas. Only a record the provider has no event for yet is checked, so events both providers had saved before this check stay twice, and when the first copy is cancelled, the next run of the other provider saves its own. The same start, not a start within some minutes, keeps a matinée and an evening show apart; the saved responses of 2026-11-03 have no such pair, so the e2e counts are unchanged.
9. **ArtWizard permits the import, on conditions.** Its public offer ([offer.pdf](https://artwizard.io/files/offer.pdf)) says the platform's databases may not be used without its permission (§11.1), and that event materials come from the organizers (§11.2). Permission was requested on 2026-11-03 and granted the same day by Vlad Lisovyk, ArtWizard's founder, by email, together with access to the API, within the scope of the request and on three conditions:
   1. Nearby stays a non-commercial study project: no ads, no paid features, and the data is not passed to third parties.
   2. The permission lasts for the duration of the study project, which ends by **2026-12-10**; the team asks again before then.
   3. ArtWizard is told in advance before the import changes how often it collects.

   The scope of the request, which the permission covers: Kyiv events for the coming 4 weeks, at most one request per second, at most one update per day, images linked and not copied, and ArtWizard credited with a link to the event page on every event.

   Commercial use needs a separate agreement. The import keeps to the Kyiv slice, links images instead of copying them, and links every event to its ArtWizard page. If the permission ends, the adapter is unbound in `ImportInfraModule` and its events are removed. Karabas' public offer has no such clause.

10. **Events the provider no longer lists are cancelled.** After a provider's run that read its **full list** (decision 2), the provider's imported events that start between the time the list was read and the end of the last day it covers, and that the run did not see, become `cancelled`: the catalog leaves them out of `GET /events`, and `GET /events/{id}` shows them as cancelled, as for an organization's cancelled event (FR-011). An event the run *saw* was saved, or skipped only because the geocoder failed or found nothing, which says nothing about whether the event exists; one skipped for any other reason is not seen, so an event stored earlier that the adapter now skips (e.g. "Я бачу, вас цікавить пітьма" at 00:00 on ArtWizard) is cancelled too. A cancelled event the provider lists again is published again. Organization events are never touched: the repository changes only events with `source` import and the run's provider. The saved ArtWizard pages hold only `published` records; a record with another status is skipped and so, once stored, cancelled.

    A failed run, a list that is not complete, or a complete one that looks broken cancels nothing, so a provider that is down or redesigned never empties the catalog (FR-014, REL-003). A complete list looks broken when it saw no records, when it saw fewer than half as many as the provider's last complete list, or when a part of the provider that listed events in that list lists none now (a Karabas section answering an empty page). Each succeeded run records in `import_runs` whether its list was complete and passed these checks, how many records it saw, and how many events each Karabas section listed; a run that did not pass is not the one the next run compares itself with.

    The import does not enqueue `event.changed` yet. The job queue (#391) is merged, but nothing consumes the job. The import is to enqueue it later in #418: `cancelUnseen` returns the ids it cancelled, and the cancellation, the republishing and a changed start time each enqueue `event.changed` with the event id and the change, in the same transaction as the change (`TransactionRunner`, [job queue](../mechanisms/job-queue.md), rule 1); `nearby_import` has the pg-boss grants for it since the `import_job_queue` migration (decision 11). Matching decides what the change means for applicants (HLD I3); the import never touches sessions or applications.

    **Known limitation: applications of a cancelled event stay active.** Cancelling changes only the event's status. Since applications exist (#374), its sessions stay `scheduled` and its applications `in_pool`, `paired` or `paused`, and the user still sees them among their applications; a new application is refused (`EVENT_CANCELLED`), and an event published again has its old applications back. A changed start time leaves the event's sessions at the old time, as they are keyed on (event, start). An organization cancelling its event (FR-011) has the same gap. Closing the pools, cancelling the applications, telling the applicants and moving or cancelling the sessions belong to an `event.changed` consumer in matching (#418).

11. **The import runs on a schedule, at most once in 20 hours per provider.** The import process runs until it is stopped and takes the `import.run` jobs of the job queue (HLD I3, [job queue](../mechanisms/job-queue.md)): one schedule per provider, keyed by its id, at `0 2 * * *` UTC with the payload `{ providerId }`, after the nightly backup at 01:00. `import.run` is never retried (`retryLimit` 0) and counts as failed after an hour; a failed run waits for the next day's job. Before a run starts, the import reads when the provider's last run started, whatever its outcome; if that is less than the provider's `minHoursBetweenRuns` ago (20 hours for both, set per adapter), it logs the time the next run may start and starts nothing, so ArtWizard's "at most one update per day" (decision 9) holds also for a repeated job, a run started by hand, or a restart. The check comes before an unfinished run is marked failed, so a run still going in another process is left alone. `node dist/import/main.js --once` (`npm run import:events`) runs every provider once and exits, with the same check; `--force` skips it, only together with `--once` and never with `NODE_ENV=production`, for local runs and the e2e tests. A provider that is unbound later keeps its schedule row, and its job does nothing.

    The check and the start of the run are two statements, not one transaction: two processes starting the same provider within the same moment could both start it. On staging only the `import` service starts runs, and pg-boss sends each occurrence of a schedule once across instances.

## Alternatives

| Option | What it does better | Why not |
|---|---|---|
| Karabas and Concert.ua | More concerts | Most are the same concerts: duplicate events and split applicants; Concert.ua needs 1 + N requests per section |
| Concert.ua instead of Karabas, or its ends matched onto Karabas events | An `endDate` on every event (78 of 78 on 2026-11-14) | 51 of the 78 ends fall exactly 2 hours after the start, its default when the organizer gives no length, so they are not real ends either; the two sites shared 30 events, 6 of them with another length, under 1 % of the Karabas events; matching them would depend on the fuzzy title match of decision 8 and on venue names, as its lists give no address. Karabas descriptions give a length for 199 events with no more requests |
| Merge duplicates across providers into one event with both sources | Both providers' details and links on one event; events saved twice before are joined too | A merged event needs a new model (several `provider`/`external_id` pairs, whose fields win), and its cancelling would depend on two lists; skipping the second copy (decision 8) gives one event per real event with the model as it is |
| Keep crawling the ArtWizard sitemap and event pages | No key to keep secret | One request per event instead of one per 20; the type tags had to be dug out of the page's Next.js data; the API is what ArtWizard permitted |
| Download images to our storage | Images survive the provider removing them | Storage and rights we do not have; ArtWizard's robots.txt disallows its image CDN |
| Paid geocoder (Google, Mapbox) | Better hit rate on informal addresses | A key and a bill for a few dozen new venues a week; Nominatim's limit is enough at Kyiv scale |
| Football club sites for sport | More matches | One adapter per club; deferred to its own issue, Karabas `/sport/` covers matches for now |

## Consequences

- The catalog has real Kyiv events from two sources; a third is a new adapter class and a line in `ImportInfraModule` (FLEX-003).
- A run takes seconds for ArtWizard (4 API pages for 74 Kyiv events on 2026-11-03) and under a minute for the Karabas pages (44 requests for 683 events on 2026-11-07, 10 of them for `/concerts/` and 25 for `/theatres/`), plus the Nominatim lookups for new venues: 121 on a first run into an empty database, about 2 minutes, and only the new venues after that.
- A change of the ArtWizard API or a redesign of the Karabas site breaks its adapter; the saved responses in `tests/unit/fixtures/providers/` pin the expected shape, and a broken adapter shows up as skipped records or a failed run, not as wrong events.
- Without `ARTWIZARD_API_KEY` the ArtWizard run fails and Karabas still runs. On staging the key is an optional secret: a deploy without it succeeds, and only the import's ArtWizard run fails.
- Imported image URLs can stop working when the provider removes them; the app then shows its gradient, as for an event without an image, unless the device still has the image cached (decision 6).
- **Known limitation: events without an end.** Most imported events still have an unknown end: on 2026-11-14, 496 of the 700 Karabas events the adapter takes and 59 of the 70 from ArtWizard. They say so (`endTimeKnown` false), and the app shows their start only, but their session still lasts until the end of the day, so matching takes applications for a 19:00 concert until late in the evening ([matching](../mechanisms/matching.md), rule 9). What matching does with an unknown end is its own decision.
- **Known limitation: runs of shows.** For now a Karabas run, written with a later midnight (a play on every day from 3 to 12 November) or with a time on a later day (a museum open daily from 10:00 to 14:00 until 1 May), is imported as its first show only, so users cannot apply for the later dates. The full schedule, one session per day ([matching](../mechanisms/matching.md), rule 9), is left for #416.
- **Known limitation: ongoing exhibitions.** An exhibition that runs through the window without opening hours, with only a 00:00–23:59:59 run in it (e.g. "Іванів ковчег. Простір свободи", open until 29 November), is skipped for now as having no start time; so is one written as a single occurrence from a past opening to its last day ("Нелінійний простір", 29 October 18:30 to 29 November), as having no occurrence in the window. On 2026-11-03 that was 15 of the 74 ArtWizard events, on 2026-11-14 the 19 exhibitions among the 27 events without a start time. The decision is taken (decision 5): a multi-day event that opens at a default 12:00, marked as a default. Its implementation is #417; until then they stay skipped.
- An event that is gone from a provider's full list is cancelled, whether the provider cancelled it, sold it out and removed it, or moved it past the window; it is published again if the provider lists it again. Until `event.changed` is enqueued and consumed (#418), its applications stay active and its applicants are not told (decision 10).
- The first run after the `import_run_lists` migration has no earlier complete list to compare itself with, since older runs count as not complete; it is checked only for seeing no records at all.
- ArtWizard leaves the catalog when its permission ends, by 2026-12-10 unless it is extended (decision 9).
- A run that failed, or that a deploy stopped, is not repeated the same day: the next one is the following night's (decision 11). An import running when its process is stopped gets 30 s to finish; otherwise it stays `running`, is marked failed by the next run, and still counts for the 20 hours.
- **Reconsider if** ArtWizard's permission ends or a commercial use is planned, another provider offers an API or a partner feed, if the same event regularly shows up from both sources under titles or start times the check of decision 8 does not join, if Karabas stops writing lengths in its descriptions or the lengths read turn out wrong, or if Nominatim's hit rate on Karabas addresses turns out too low.
