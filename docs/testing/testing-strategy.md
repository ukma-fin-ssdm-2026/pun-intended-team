# Testing Strategy

How Nearby is tested today and how testing will grow with the project. Requirements are in [`requirements.md`](../requirements/requirements.md), user stories in [`user-stories.md`](../requirements/user-stories.md).

## Current Status

Tests use the Node.js test runner (`node:test`), and coverage is measured with [c8](https://github.com/bcoe/c8) ([`.c8rc.json`](../../.c8rc.json)). All tests import the built code from `dist/`, because Node cannot run the decorators in `src/` directly.

| Suite | File | What it checks |
|---|---|---|
| Unit | [`events.unit.test.ts`](../../tests/unit/events.unit.test.ts) | FR-010: the event body rejects each missing field; FR-011: only the owner can cancel an event, and cancelling twice changes nothing |
| Unit | [`auth.service.test.ts`](../../tests/unit/auth.service.test.ts) | FR-005 / SEC-008: a code older than 10 minutes is rejected; FR-001: sign-in issues a token with the account role and a new session id |
| Unit | [`listings.service.test.ts`](../../tests/unit/listings.service.test.ts) | FR-021: no listing for a cancelled event; only the author can delete a listing |
| E2E | [`api.e2e.test.ts`](../../tests/e2e/api.e2e.test.ts) | Starts the built API against PostgreSQL and calls every endpoint over HTTP: one valid request and the rejections for each. Includes the bad-token cases of SEC-005 and the code limits of SEC-008 |

There are 14 unit tests in 4 suites (all pass) and 88 e2e tests in 27 groups. Repositories are mocked in unit tests, so unit tests need no database or server.

## Integration, System and Acceptance Tests

- **Integration.** Today the only code that reaches the real database is `prisma-categories.repository.ts`, and only the e2e suite exercises it. Each stub repository that gets replaced by a Prisma one (ADR-002) will get integration tests against the Docker PostgreSQL. Later, the suite will also run against two API instances to check FLEX-002.
- **System.** The e2e suite is our system test: the built API, a real database, HTTP only. Each new endpoint (matching, notifications, reports, bans) will get e2e tests the same way.
- **Acceptance.** Each acceptance criterion in `user-stories.md` will become a named e2e scenario, traced in [`rtm.md`](../requirements/rtm.md). US-001–US-004 and US-010 have endpoints now; US-005–US-009 (bans, map, reports, matching) follow when they are built. Before the final demo, the core flows get the manual pass that COMP-001 requires.

## Performance, Security and Property-Based Testing

- **Performance.** A k6 scenario for PERF-001: 500 concurrent sessions for 10 minutes against staging, asserting p95 ≤ 1000 ms, p99 ≤ 2000 ms and maximum ≤ 5000 ms. A second k6 scenario for PERF-003 once matching exists: 50 users request a match on one event within 10 seconds, asserting p90 ≤ 60 s.
- **Security.** `npm audit --audit-level=high` already runs in CI for all three packages (SEC-006). Once matching exists, SEC-001 gets authorization tests for each match state (proposed, one-sided accept, mutual accept, rejected), run as an unauthenticated user and as a banned user.
- **Property-based.** A fast-check test of the pure `match(pool, exclusions, seed)` function ([matching mechanism](../architecture/mechanisms/matching.md)) over random pools, checking FUNC-002: every pairing is mutual, no user is in two pairings of a round, and no excluded pair is matched. The same test can check FUNC-001: the same seed always gives the same ordering.

## CI/CD

Today [`ci.yml`](../../.github/workflows/ci.yml) has one job, `CI passed`. It runs lint, formatting, type checks, the client checks, the OpenAPI spec check, `npm audit`, the database migrations and `npm run test:e2e`. It runs no unit tests and no coverage.

The checks were merged into a single job because GitHub Actions bills every job separately. Even so, GitHub Actions stopped when the organization ran out of minutes.

Plan: once the self-hosted runner works, the e2e step will be replaced by `npm run test:coverage` (unit + e2e) on every pull request, with `c8 --check-coverage` failing the build below a threshold. The generated Prisma client is excluded first. The target is MAIN-001: at least 70% statements on the API, and at least 85% on matching, the authorization guards and the report/ban flow.
