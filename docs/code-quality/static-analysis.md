# Static Analysis and Security Review

Security analysis of the Nearby REST API for Lab 5. This document covers the manual security review. The automated analyzer results and the dependency audit are added in separate changes (see the sections below).

## Manual security review

### Scope

All hand-written server code under `src/` at commit `55400b8` (branch `feature/126-security-analysis`):

- `src/api/main.ts`, `src/api/app.module.ts`
- `src/api/common/`: `config.ts`, `auth.ts`, `endpoint.ts`, `api-exception.ts`, `api-exception.filter.ts`, `api-express-adapter.ts`, `openapi.ts`, `registry.ts`, `routes.ts`, `schemas/`
- `src/api/catalog/`, `src/api/listings/`, `src/api/system/`: all controllers and zod schemas (16 endpoints)
- `src/core/`: services, repository interfaces and types (identity, catalog, listings, profiles, common)
- `src/infra/`: `infra.module.ts` and every stub repository, including `stubs/data.ts`
- Configuration that affects the running API: `.mcp.json`, `.env.example`

Out of scope: `src/mcp/` (generated by openapi-mcp-generator from the spec), third-party packages (covered by the dependency audit), and infrastructure that does not exist yet (TLS, load balancer, database).

### Method

1. Read every file in scope, following each request from the Express adapter through the global guard, the `@Endpoint` interceptors and the handler to the exception filter.
2. Checked each area against the threat model ([threat-model.md](../architecture/threat-model.md)) and the security requirements ([requirements.md](../requirements/requirements.md), §4.3 and INTC-004): authentication and access control, input validation, response shaping, error handling, transport and HTTP hardening, configuration defaults, committed credentials.
3. Searched for handlers that bypass `@Endpoint` (raw `@Get`/`@Post`/`@Body`/`@Query`/`@Param`/`@Req` decorators). None were found.
4. Confirmed the findings against a running server: `npm run build`, then `NODE_ENV=production PORT=4199 node dist/api/main.js`, probed with `curl` (status codes, response headers, error bodies, oversized and malformed bodies, 150 requests in a row).

No rule IDs apply: every finding below comes from manual review, not from a tool.

### Findings

Risk: **High**: exploitable now or as soon as the API is deployed, with access-control impact. **Medium**: a weakness that needs a misconfiguration or has limited impact today. **Low**: hardening gap.

#### SA-01 in full: inherited object properties accepted as access tokens

- **What was found.** `StubSessionsRepository.findCaller` returns `sessions[accessToken]`, where `sessions` is an object literal (`src/infra/stubs/data.ts:22`). A plain object inherits from `Object.prototype`, so for the token `constructor` the lookup returns the `Object` function, for `__proto__` it returns `Object.prototype`, and so on. Neither is `undefined`, so `AuthService.authenticate` reports a caller. `AuthGuard` (`src/api/common/auth.ts:41`) then checks only `caller.kind !== 'account'` before rejecting `user` and `admin` access, and lets every other value through as a guest.
- **How it was found.** Manual review of the authentication path, guard → `AuthService` → `SessionsRepository`, with no rule ID. Confirmed on a running server: `Authorization: Bearer constructor` (also `__proto__`, `toString`, `hasOwnProperty`) gets `200` on `GET /api/v1/categories` and `GET /api/v1/events`, while `Bearer bogus` gets `401`. `user` and `admin` endpoints still answer `401`.
- **Why it is a risk.** SEC-005 requires protected endpoints to reject an invalid token with `401` in 100% of cases, and TM-11 relies on deny-by-default guards. Today the impact is small: the guest tier only reads the catalog, which an anonymous guest token unlocks anyway. But the per-token rate limits planned for SA-04 and TM-10 would count requests against a token that is not issued to anyone, and the guard's deny-list check (anything that is not an account is a guest) would let any future `Caller` kind, or a repository bug that returns an unexpected value, through as a guest.
- **Decision: to be fixed in #129.** This task changes no code. The fix: look tokens up with `Object.hasOwn` or a `Map` in the stub repository, and make the guard allow-list (`caller.kind === 'guest'` for guest access, otherwise reject with `401`). Add an e2e test that `constructor` and `__proto__` get `401`. The real JWT-based session repository must keep the same property: an unknown token never resolves to a caller.

#### SA-02 in full: Swagger UI and spec rewrite enabled unless `NODE_ENV=production`

- **What was found.** `isProduction = process.env.NODE_ENV === 'production'` and `serveSwaggerUi = process.env.SWAGGER_UI === 'true' || !isProduction` (`src/api/common/config.ts:7-9`). Every value other than the exact string `production` counts as development: unset, `prod`, `staging`, `Production`. In development mode `main.ts` serves Swagger UI with "Try it out" and the raw spec at `/api-docs` and `/api-docs.json`, and writes the spec file to the repository path on every start.
- **How it was found.** Manual review of `config.ts` and its uses in `main.ts`, with no rule ID. Confirmed that with `NODE_ENV=production` `/api-docs` answers `404`. The opposite case follows directly from the code. `.env.example` sets `SWAGGER_UI=false` next to `NODE_ENV=development`, but in that combination Swagger is still served, because `SWAGGER_UI` can only turn it on.
- **Why it is a risk.** A deployment that forgets `NODE_ENV` exposes an interactive console against the live API, and the spec with the stub token list (SA-03). It also tries to write into the deployed file system. The safe behaviour depends on an environment variable being set exactly right, which makes this a fail-open default.
- **Decision: accepted.** `NODE_ENV=production` is a mandatory setting of every deployed environment and must be part of the deployment configuration and checklist. The behaviour in development, where Swagger runs and the spec refreshes on start, is what the team relies on locally. The spec and Swagger UI are already public on GitHub Pages, so a forgotten variable mainly exposes "Try it out". The risk is revisited if a deployment is ever found running without `NODE_ENV=production`, or when the stub tokens of SA-03 are removed. The alternative, treating every environment except an explicit `development` as production, was considered and not chosen.

### What is done well

- **Deny by default.** `AuthGuard` is global (`APP_GUARD`), and an endpoint without an access level is treated as `user` (`auth.ts:31`), so a forgotten declaration fails closed.
- **No resource or role disclosure.** A non-admin calling `/admin/*`, any `403`, and access to another organization's event or another user's listing all answer `404 NOT_FOUND`, as if the object did not exist (`api-exception.filter.ts:52`, `auth.ts:44`, `events.service.ts:76`, `listings.service.ts:68`).
- **One validation path for every endpoint.** All 16 endpoints are declared with `@Endpoint`, which validates params, query and body with zod before the handler runs and passes only the parsed values. Request bodies are `z.strictObject`, so fields such as `organizationId`, `status` or `source` are rejected (verified: `400` "Unknown fields are not allowed"). Strings have length limits, IDs must be UUIDs, and page size is capped at 20 with no total count.
- **Responses are shaped by the declared schema.** `ResponseSchemaInterceptor` parses every success result with its zod schema, which drops internal fields such as `organizationId`, `authorId` and `accountId`. A result that does not fit becomes a logged `500`.
- **Errors never leak internals (INTC-004).** `ApiExceptionFilter` is the only place that builds error bodies. Unexpected exceptions are logged with their stack and returned as `INTERNAL_ERROR` / "Something went wrong". Nest's own messages ("Cannot GET /path") are replaced. Malformed JSON, oversized bodies and broken percent-encoding map to clean `400`/`413` responses (all verified). Domain error messages are fixed strings with no user input in them.
- **Express hardening.** JSON body limit of 100 kB, `x-powered-by` disabled (both verified), no CORS enabled, so browsers on other origins cannot call the API.
- **Least privilege in tooling.** `.mcp.json` gives the MCP server `stub-guest` only, not a user or admin token.
