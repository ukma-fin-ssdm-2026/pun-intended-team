## 4. Співпраця та робочий процес

### Стратегія гілкування
- GitHub Flow: гілка `main` завжди робоча, прямі пуші в неї заборонені.
- Уся розробка ведеться в короткоживучих гілках, що створюються від `main`.
- Формат назв гілок: `<тип>/<короткий-опис>` (наприклад, `feature/product-crud`).
- Основний тип гілок: `feature`.
- Роботу по можливості розподіляємо за модулями/фічами, щоб мінімізувати конфлікти між учасниками.

### Практики комітів
- Коміти атомарні — один коміт відповідає одній логічній зміні.
- Формат повідомлення: `(#номер-issue) Короткий опис у наказовому способі` — наприклад, `(#3) Write initial README`.
- Мова повідомлень комітів — англійська.
- Перед комітом гілку синхронізуємо з `main` через rebase, щоб уникати зайвих merge-комітів.

### Огляди коду (Code Review)
- Злиття в `main` можливе лише через pull request.
- Обов'язкове щонайменше 1 схвалення від іншого учасника команди; якщо це підзадача — схвалення потрібне від людини, відповідальної за цю задачу.
- Автор PR перевіряє, що код працює локально, перед тим як запросити рев'ю.
- Рев'юер відповідає протягом 48 годин; якщо відповіді немає — писати в загальний чат команди.
- При незгоді рішення ухвалюється коротким обговоренням у чаті/дзвінку, а не одноосібно.
- Гілку можна закривати лише тоді, коли виправлено всі зауваження щодо неї.

### Робочий процес завдань
- Завдання ведемо в GitHub Issues.
- Завдання призначає собі виконавець самостійно з дошки To Do (з урахуванням лімітів кількості обраних завдань).
- Визначення готовності: код злитий у `main`, PR закрито, функціональність перевірена вручну.
- Гілку після злиття PR видаляємо.

## 5. Вирішення конфліктів
1. Пряма розмова між учасниками, яких стосується розбіжність — спершу спробувати домовитися без залучення всієї команди.
2. Якщо не вдалося — питання виноситься на найближчу командну зустріч для обговорення.
3. Якщо консенсусу немає — голосування більшістю голосів.
4. Якщо конфлікт не вдається вирішити всередині команди (включно з міжособистісними суперечками, що заважають роботі) — ескалація до викладача проєкту.

Усі рішення, ухвалені через голосування або ескалацію, фіксуються письмово (у чаті команди або протоколі зустрічі), щоб уникнути повторного відкриття питання.
